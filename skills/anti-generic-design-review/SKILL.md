# Anti-generic design review

An interface looks "made by AI" when every choice is the default one. The fix is not decoration: it is replacing each default with a decision that only makes sense for this product, this audience and this content.

## How to review

1. Read the art direction (references, tone, what to avoid) and the page's purpose. Without them you can only judge taste, so ask for them first.
2. Capture the page and look at the captures, not at the code (see the screenshot loop below), then go through the traits below, one by one.
3. For each trait found, write where it is, why it reads as generic here, and the replacement decision. "Make it more original" is not a replacement.
4. Check that each replacement still meets the design system: tokens, contrast AA, focus states and the type scale.
5. After the replacements are applied, capture again at the same widths and compare with the first round. A fix that only looks right in the code is not done.

## Screenshot loop

Review what the browser renders, at three widths: **390 px** (phone), **768 px** (tablet) and **1440 px** (desktop).

- Use Playwright from the project if it is already a dependency, or the Playwright tooling the user has approved. Ask the user before installing browsers or packages, and never install them globally on their machine.
- Open only local files, a local dev server or a preview URL the user gave you. Do not log in, submit forms or click through payment or account flows.
- Capture full-page screenshots, one per width, named `<page>-<width>.png`, into a folder the user agrees on (for example `design-review/`), and keep that folder out of git unless the user wants the captures committed.
- Look at every capture before writing findings. Check what code reading misses: overflow and horizontal scroll, text that wraps badly, elements that collide, images cropped wrong, and a hierarchy that only works at one width.
- If no browser is available, say so in the output and review the code and the mockups instead; do not claim you looked at the page.

## Generic traits and their replacements

| Trait | Why it reads as generic | Replace it with |
|---|---|---|
| Default gradients (purple to blue, violet to pink) on the hero or buttons | It is the template default, so it says nothing about the brand | Flat brand colors from the palette; a gradient only if the art direction asks for it, built from brand colors and used in one place |
| Rows of identical cards, each with a generic line icon, a title and two lines of text | Interchangeable with any other site; the icons carry no information | Vary the layout by importance; replace icons with real evidence (a screenshot, a number, a client name, a photo of the actual work), or drop the cards and write a list |
| Empty headlines ("Transform your business", "Unlock your potential", "The future of X") | They could sit on any product and promise nothing verifiable | Say what the product does, for whom and with what result, using the audience's words and the keyword map; a concrete number or deadline beats an adjective |
| Default type (the system or template font everywhere, at near-equal sizes and weights) | No hierarchy, so the eye has no entry point | A type pairing chosen in the art direction, a clear scale with few sizes, and weight and size contrast between heading, lead and body |
| Uniform spacing (the same gap between every block) | Everything looks equally important and the page reads as a stack | A spacing scale used with intent: tight inside a group, generous between sections, extra space around the one thing that matters |
| Stock or generated illustrations (3D blobs, floating people, abstract waves) | Seen everywhere; they show nothing true about the product | Real product screenshots, photos of the team or the work, or a simple diagram that explains something; if there is nothing real yet, use type and color instead of filler |
| Everything centered, every section the same width | No rhythm and no reading path | Left-aligned text for anything longer than a line; vary width and alignment between sections to set a path |
| Decorative glow, glassmorphism, oversized rounded corners and shadows on everything | Effects stand in for decisions | One elevation and radius style from the tokens, used consistently and sparingly |
| Placeholder social proof (fake logos, invented testimonials, "Trusted by 10,000+") | Unverifiable claims destroy trust and can be illegal | Real, approved proof only; otherwise remove the section |
| Warm cream or paper base (for example #F4F1EA) with a terracotta, vermilion or brick accent, often with a serif or mono "editorial" type | The "paper and ink" look is a default that keeps reappearing in generated interfaces; the palette comes from a mood, not from the brand | Derive the palette from one attribute of the brand or the content; use a cool or white base and an accent outside the red-orange family; verify contrast with a computed ratio |
| Default "software blue" accent (a saturated mid blue on a white or cool grey base) or a "midnight" dark mode (navy or blue-black background with a light blue accent) | It is the most common blue in software, so the product blends into every other tool and the palette says nothing about the brand | Derive the hue from one attribute of the brand or the content; test the accent against the direct competitors so it does not compete with their blue; build the dark mode from the same hue logic, not from a default blue-black; verify contrast with computed ratios |
| Emoji as icons in headings and lists | Signals a template, renders differently on every platform | The icon set from the design system, or no icon |

The list is not a ban. A trait is fine when the art direction asks for it on purpose and the review can say why it fits this brand.

## Rules

- Judge against the art direction and the content, not your personal taste.
- Never fix one trait by introducing another (for example, swapping a purple gradient for a teal one).
- Replacements must use the design tokens; if a new token is needed, propose it to the designer instead of hard-coding a value.
- Reference other sites as patterns only; never copy their layout, illustrations or copy.

## Output

```
Verdict: ready | ready with changes | rework
Captures: before and after, at 390, 768 and 1440 px (paths), or "no browser available"
Generic traits found:
- where (page/section or file:line) — trait — why it is generic here — replacement decision
Kept on purpose:
- trait — reason from the art direction
```

## Known failures

_Record real mistakes here with a date and the rule that prevents them._

- 2026-10-28: A design review passed a landing built on a warm cream base (#F4F1EA) with a vermilion accent and an editorial serif, because it looked refined and had no purple gradient. That is the same default in a different costume. Look: warm paper base, accent in the burnt red-orange family (terracotta, vermilion, brick), serif or mono "editorial" type. Why generic: it is the "paper and ink" look generated interfaces fall back to, chosen for mood rather than for the brand. Detect it with this checklist: (1) is the base a warm off-white or cream? (2) is the accent terracotta, vermilion or brick? (3) can you name the brand or content attribute that produced this palette? If (1) and (2) are yes and (3) is no, flag it. Replace it with a deliberate decision: derive the palette from a brand or content attribute, use a cool or white base with an accent outside the terracotta family, and verify contrast with computed ratios, not by eye. Keep it only if the art direction explicitly asks for it and states why.
- 2026-10-28: A design review passed a landing with a saturated mid-blue accent on a white base and a navy dark mode with a light blue accent, because it was clean and had no gradient. That is the default "software blue" and the default "midnight" dark mode. Look: a pen-ink or software blue accent (medium, saturated) on white or cool grey; dark mode with a navy or blue-black background and a light blue accent. Why generic: it is the blue most software already uses, so it competes with the products around it, and the dark mode is the default of the tools, not a choice. Detect it with this checklist: (1) does the accent hue come from the brand or the content, or is it the default blue? (2) is the dark mode a blue-black by default? (3) can you name the attribute that produced each? If (1) or (2) is the default and (3) is no, flag it. Replace it with a deliberate decision: derive the palette from a brand or content attribute, test the accent against the direct competitors, and verify contrast with computed ratios, not by eye. Keep it only if the art direction asks for it and states why.
